**Architect decision (Claude), for Codex to implement next — the restore/Trash mutual-exclusion lock.** Codex correctly declined to implement my originally-suggested cheap fix ("`restore()` refuses once `permanent_delete_confirmed_at` is set") because it would break v11's explicit guarantee that restore stays available *after* Trash confirmation, right up until the Trash move itself begins. 1. **Migration 005:** add `'restoring'` and `'trashing'` to `batches.status`'s CHECK constraint (same rebuild-table approach as migration 004), as transient "a live write of this kind is in progress or was interrupted" markers — not terminal states, exactly like `'labeling'`.
2. **`restore()`:** widen the entry check from `status == 'restore_window'` to `status in {'restore_window', 'restoring', 'failed'}` (the latter two support resuming an interrupted restore, matching `archive()`'s `{'approved','labeling','failed'}` shape). AND status='restore_window'`. If 0 rows are affected, someone else already moved it away from `restore_window` — raise the existing "Only restore-window batches can be restored" error unchanged.
3. **`trash()`:** keep every existing check exactly as-is, **including the confirmation-hash re-validation and the `permanent_delete_confirmed_at` requirement — none of that is loosened or reordered.** Only immediately before calling `_write_trash()`, add the symmetric atomic claim: `UPDATE batches SET status='trashing' WHERE batch_id=? 4. This closes the race with one atomic `UPDATE ... WHERE status=?` per operation — no new locking primitive, no polling. The only thing that can now block a competing operation is the other one having **actually started writing to Gmail**, which is the correct, spec-consistent line (not merely having been confirmed).

**Live-run finding #10 (2026-09-22) — new, open. Concurrent live executions collectively exceed the same quota wall.** While reviewing the above fixes against the real database, found three *additional* batches beyond the three I'd manually retried: `comparably.com` (148 msgs), `xt2.kgbdeals.com` (104 msgs), `locboxlabs.org` (87 msgs). This is a new failure mode, not a regression of the finding #8 fix — my three sequential, one-at-a-time retries immediately prior all succeeded cleanly using this exact same paced code. The difference here is **concurrency**: `review-ui/executor.py`'s `invoke()` launches each action via `subprocess.Popen` with no serialization at all, so nothing stops three "Start Archive" clicks in quick succession from spawning three independent executor processes, each correctly paced *on its own* (10 messages/2 seconds) but **collectively** stacking their request rates against the same per-account quota that a single paced stream was already tuned to sit right under. Three concurrent paced streams ≈ 3x the tuned rate ≈ right back into the wall.

No data lost or corrupted — all three failed batches are safely resumable the same way as finding #8's (some already-preflighted messages may be `labeled`, rest stay `pending`).

**Recommended fix for Codex:** serialize live executor invocations at the one common entry point, `review-ui/executor.py`. Simplest correct shape: a single background worker thread owned by the review-ui process, fed by a queue; `invoke()` enqueues `(script, arguments)` instead of calling `Popen` directly, and the worker runs one subprocess to completion before starting the next. HTTP endpoints keep returning immediately (unchanged UX — "archive_requested" today already implies async completion); only the actual Gmail-writing subprocesses become strictly one-at-a-time. This keeps `execute/`'s own tested logic completely untouched — the fix belongs entirely in the UI's dispatch layer, not the executor.
